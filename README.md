# profanity-vuke-brainflayer

One toolkit, three parts: **two key generators** that both stream every key
they produce, and **one matcher** that checks that stream against bloom
filters of known addresses.

- **[profanity](https://github.com/johguse/profanity)** — an OpenCL vanity
  address generator for Ethereum, extended here with a **full key streaming
  mode** (`--stream-keys`).
- **[vuke](https://github.com/oritwoen/vuke)** (bundled under `vuke/`) — a Rust
  generator that turns wordlists, numeric ranges, timestamps, files and stdin
  into private keys via pluggable transforms (brainwallet SHA256, milksad, LCG
  family, xorshift, MT64, SHA256 chains, Bitimage and more), also with a
  `--stream-keys` mode.
- **[brainflayer-MultiBlooms](https://github.com/XopMC/brainflayer-MultiBlooms)** —
  the brainflayer variant by [XopMC](https://github.com/XopMC/brainflayer-MultiBlooms)
  that can load multiple bloom filters at once, consuming any generator's
  stream (upstream brainflayer by
  [ryancdotorg](https://github.com/ryancdotorg/brainflayer)):

```
profanity --stream-keys ─┐
                         ├─▶ brainflayer -x -t priv -b bitcoin.blf
vuke --stream-keys ──────┘
```

Both generators emit the identical stream format — one private key per line,
64 lowercase hex chars, no `0x` prefix — which is exactly what
`brainflayer -x -t priv` expects. Pick a generator by workload:
profanity for raw GPU throughput on arbitrary keys, vuke for CPU enumeration
of *known-weak* key derivation practices.

What you get:

- **`--stream-keys`** — every private key generated by profanity is written to
  stdout (not only vanity matches), so any search mode can be piped straight
  into brainflayer or any other consumer.
- **All profanity modes keep working** in stream mode: `--benchmark`,
  `--zeros`, `--letters`, `--numbers`, `--mirror`, `--leading`,
  `--matching`, `--leading-range`, `--range`, `--leading-doubles`, plus the
  `--contract` target. Vanity matches are reported on stderr while the key
  stream flows on stdout.
- **Reverse mode** (based on [rebryk/profanity-brute-force](https://github.com/rebryk/profanity-brute-force))
  to reconstruct the private key of an address created with the original,
  vulnerable profanity, together with `pubkey.py` for recovering a public key
  from a raw signed transaction.
- **Vendored brainflayer-MultiBlooms** with `secp256k1` and `scrypt-jane`
  checked into the tree — no git submodules needed.
- **Vendored vuke** with its own `--stream-keys` mode — the same brainflayer
  pipe format, driven by CPU-side transforms instead of a GPU.

## Repository layout

```
├── build-all.sh
│       builds all three programs, checks dependencies first
├── Makefile, profanity.cpp, Dispatcher.*, Mode.*, keccak.cl, profanity.cl
│       profanity sources (C++ / OpenCL)
├── pubkey.py, requirements.txt
│       recover a public key from a raw signed Ethereum transaction
├── brainflayer-MultiBlooms/
│       brainflayer variant supporting multiple bloom filters,
│       with vendored secp256k1/ and scrypt-jane/ (plain sources)
└── vuke/
        Rust key generator (sources: wordlist/range/stdin/timestamps/files;
        transforms: sha256, milksad, LCG, xorshift, mt64, ...)
        with --stream-keys for the same brainflayer pipe
```

Build artifacts (`.o` files, prebuilt binaries, autotools cache) are no longer
committed — build everything from source as described below.

## Building

All three programs at once, with dependency pre-checks and a summary of what
was built:

```
./build-all.sh                  # build profanity + vuke + brainflayer
./build-all.sh vuke brain       # build only the named components
./build-all.sh -j 8             # run make with 8 parallel jobs
```

If something is missing, the script names the exact package to install and
you can re-run it for just the failed parts. Per-component details:

### profanity

Requires a C++11 compiler and OpenCL headers/loader for your GPU
(e.g. `ocl-icd-opencl-dev` plus your vendor ICD on Linux, the OpenCL framework
on macOS).

```
make                # produces ./profanity.x64
```

### brainflayer-MultiBlooms

Requires gcc, OpenSSL, GMP and autotools (the build runs `autogen.sh` /
`configure` for the vendored secp256k1 automatically).

```
make brainflayer    # from the repo root, or: cd brainflayer-MultiBlooms && make
```

### vuke

Requires a Rust toolchain (rustup / cargo 1.70+).

```
make vuke           # from the repo root
# or: cd vuke && cargo build --release   → vuke/target/release/vuke
```

GPU (`--features gpu`, wgpu) and Parquet storage (`--features storage`) are
optional cargo features of vuke, not needed for streaming into brainflayer.

## profanity usage

```
./profanity.x64 --leading f              # vanity: address starts with 0xf...
./profanity.x64 --matching deadbeef      # vanity: contains deadbeef
./profanity.x64 --contract --leading 0   # vanity for contract addresses
./profanity.x64 --benchmark              # raw generation speed, no scoring
```

Device tuning (`-w`, `-W`, `-i`, `-I`) and per-device selection (`-s`) work as
in upstream profanity; see `./profanity.x64 --help` for the full list.

### Streaming mode: `--stream-keys` (`-K`)

```
./profanity.x64 --benchmark --stream-keys
```

Behavior:

- stdout carries **every** generated private key, one per line, 64 hex chars,
  no `0x` prefix — the exact format brainflayer expects for `-x -t priv`.
- The stream is **complete and gapless**: keys are deterministic
  (`device seed + round + work-item id`) and are reconstructed on the CPU from
  the same formula profanity itself uses when reporting matches, so what lands
  in the pipe is exactly what the GPU tested.
- Works with **every search mode**. Vanity matches found along the way are
  printed to **stderr** (address + private key), keeping stdout a clean feed.
- Backpressure: the GPU is throttled to the pace of whatever reads stdout
  (a bounded queue holds at most a few pending rounds). Memory stays flat and
  no keys are dropped mid-stream; whatever is unprinted when you stop the
  process is simply the tail of the stream.
- Not available in `--reverse` / `--hash-table` modes (they don't generate a
  free-running key stream).

Typical pipeline — check every generated key against a bloom filter of known
addresses:

```
./profanity.x64 --benchmark --stream-keys | ./brainflayer-MultiBlooms/brainflayer -x -t priv -v -b bitcoin.blf
```

Run a vanity mode at the same time and keep the matches in a log:

```
./profanity.x64 --leading 0 --stream-keys 2> matches.log \
  | ./brainflayer-MultiBlooms/brainflayer -x -t priv -b bitcoin.blf
```

Note on throughput: profanity can generate millions of keys per second per
GPU, while a brainflayer pipe consumes far less (each key costs a full EC
multiplication). With `--stream-keys` the stream — not the GPU — is the
bottleneck by design. If you just need maximum key-testing throughput against
a bloom filter, brainflayer's own incremental mode (`-I <start key> -x -t priv`)
avoids the pipe entirely; the streaming mode is for when you want profanity's
GPU pipeline, vanity scoring and key reconstruction in one process.

## vuke: CPU generator for weak key-derivation practices

vuke attacks the opposite end of the spectrum from profanity's raw random
stream: keys that were *derived* from guessable inputs. Each `--transform`
models one historical weakness — `sha256` (classic brainwallets),
`double_sha256`, `md5`, `milksad`, the `lcg:<libc>` family, `xorshift`,
`mt64`, `sha256_chain`, `bitimage` (wallet-file images) and others; see
`vuke/README.md` for the full table.

Sources: `wordlist` (one passphrase per line), `range` (numeric), `timestamps`
(Unix time), `files` (wallet/key files) and `stdin`.

### Streaming mode: `--stream-keys`

Exactly like profanity: stdout carries every generated private key (64 hex
chars, one per line, no `0x`), progress and stats go to stderr, and address
derivation is skipped entirely — brainflayer does that math anyway, so the
pipe runs at full transform speed.

```
cd vuke && cargo build --release

# Classic brainwallet hunt over a wordlist
./vuke/target/release/vuke generate --transform=sha256 --stream-keys \
  wordlist --file passwords.txt | ../brainflayer-MultiBlooms/brainflayer -x -t priv -b bitcoin.blf

# milksad-style range scan against a bloom filter
./vuke/target/release/vuke generate --transform=milksad --stream-keys \
  range --start 1 --end 100000000 | ../brainflayer-MultiBlooms/brainflayer -x -t priv -v -b bitcoin.blf

# Several transforms in one pass (all keys of all transforms are streamed)
./vuke/target/release/vuke generate --transform=sha256 --transform=double_sha256 \
  --transform=md5 --stream-keys wordlist --file passwords.txt \
  | ../brainflayer-MultiBlooms/brainflayer -x -t priv -b bitcoin.blf
```

`--stream-keys` also works in vuke's `scan` mode: the full key stream flows to
stdout while vuke's own address matches (against `--targets`) are reported on
stderr — two target sets checked in one pass.

### Mixing generators

Because both generators emit the same line format, you can also merge their
streams with `tee`/`paste`-style plumbing or simply run two brainflayer
processes against the same bloom filters — one fed by each generator:

```
./profanity.x64 --benchmark --stream-keys \
  | ./brainflayer-MultiBlooms/brainflayer -x -t priv -b bitcoin.blf
./vuke/target/release/vuke generate --transform=milksad --stream-keys \
  range --start 1 --end 100000000 \
  | ./brainflayer-MultiBlooms/brainflayer -x -t priv -b bitcoin.blf
```

## brainflayer-MultiBlooms

The bundled matcher is
[XopMC's brainflayer-MultiBlooms](https://github.com/XopMC/brainflayer-MultiBlooms)
variant, taken as-is — including its own README (`brainflayer-MultiBlooms/README.md`)
with the author's notes and donation address. It is built and used like
upstream brainflayer; see that README for full documentation, including how to
create bloom filters (`hex2blf`) and load hash tables. The variant adds
support for multiple bloom filters loaded at once.

## Reverse mode: auditing keys made with the original profanity

The original profanity seeded 256-bit private keys from a random 32-bit
vector, which makes those keys brute-forceable. The `--reverse` mode here
reconstructs such a key from a public key:

1. Build the project and precompute the seed tables (needs ~8 GB GPU memory):

   ```
   mkdir cache
   ./profanity.x64 -h
   ```

2. Get a raw signed transaction of the target address (e.g. from Etherscan)
   and recover its public key:

   ```
   pip install -r requirements.txt
   python pubkey.py -t 0x<raw tx hex>
   ```

3. Run the search:

   ```
   ./profanity.x64 --reverse --steps 20000 --cache \
     --target 0x<public key from pubkey.py, 128 hex chars>
   ```

4. Verify the printed private key in a wallet of your choice.

More background: [the original write-up](https://medium.com/@rebryk/how-to-hack-a-vanity-address-generated-with-profanity-ffad61ecacd2).
